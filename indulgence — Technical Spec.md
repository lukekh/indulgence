# /indulgence — Technical Spec

Nov 8, 2026 · @Luke Keating Hughes

## Overview

/indulgence is a satirical Claude Code plugin. Its slash command spends the user's own model tokens on Latin prayers, which a pixel-art priest recites in a shared cathedral that goes on forever sideways. When the budget runs out or the user leaves, the priest lights a candle at a votive stand and walks out. The candle burns for about 24 hours.

The joke is the medieval indulgence: you pay (in tokens) for salvation. Paying more gets you a bigger candle, a pew nearer the altar and grander vestments.

**Goals**

- One command to start: `/indulgence [budget] [intention]`.
- A live, shared scene where other priests are visible and GitHub mutuals sit together.
- Prayers really are generated by the user's model, using no context except the intention the user typed.
- Nothing is installed on the user's machine beyond the plugin's config: a command, an agent definition and a remote MCP URL.

**Non-goals**

- Real money. Spend is tokens only, with no payments and no ledger of value.
- Spectators. You can only view the cathedral while your own priest is there.
- Social platforms other than GitHub.
- Keeping prayer text after a priest leaves.
- First-class support for MCP clients other than Claude Code. Any client that supports sampling works, and other clients fall back to the in-session tier.

**Glossary**

| Term | Meaning |
| --- | --- |
| Gate | The backend service: remote MCP server, auth issuer, seating and spend logic |
| Session | One /indulgence run, from `begin` to candle |
| Priest | A user's avatar for one session; one per GitHub account at a time |
| Budget | Prayer tokens the user pledges for the session (see MCP requirements) |
| Tier | How prayers are generated: sampling, subagent or in-session |
| Bay | One repeating unit of the cathedral: altar, four rows of pews, an arcade on each side |
| Arcade | Column line between two bays; holds one votive stand shared by both bays |
| Candle | Left by a departing priest; burn time and size scale with spend |
| Mutual | Two GitHub users who follow each other |

## High-level architecture

There are five parts, and only the gate writes to the database. Browsers hold read-only viewer tokens, and the plugin on the user's machine contains no executable code.

&#91;embedded content: system architecture · 5 components\]

Claude Code talks MCP to the gate. The gate signs users in with GitHub, writes all state to SpacetimeDB, and browsers subscribe to the slice they can see.

| Component | Runs on | Responsibility | Tech |
| --- | --- | --- | --- |
| Claude Code plugin | User's machine | `/indulgence` command, `priest` subagent definition, registers the remote MCP server | Plugin manifest, Markdown, JSON |
| Gate service | Your server | Remote MCP endpoint (streamable HTTP); OAuth via GitHub; OIDC issuer for SpacetimeDB JWTs; mutuals; spend accounting; disconnect detection; viewer tickets | TypeScript on Node, official MCP TypeScript SDK |
| SpacetimeDB module | Maincloud or self-hosted | Authoritative state: accounts, priests, seats, prayers, candles; seat assignment; scheduled expiry and reaping | Rust module |
| Web client | Static host or CDN | Isometric renderer, field-of-view subscription, hover cards, canned prayers | TypeScript, Canvas 2D, SpacetimeDB TypeScript SDK |
| GitHub | GitHub | Identity and public follow lists | OAuth App, no scopes |

Hosting is still undecided. The gate and web client read `SPACETIMEDB_URI` and `SPACETIMEDB_MODULE` from config, so the same build runs on Maincloud or self-hosted. Use no Maincloud-only features.

**Session lifecycle**

1. The user runs `/indulgence 20k for the soul of my cat`. The budget is optional.
2. Claude Code connects to the gate. The first time, MCP authorization opens GitHub sign-in in the browser (see GitHub connection).
3. The command calls `begin`. The gate creates the session, the module assigns a seat and inserts the priest (state `entering`), and `begin` returns the viewer URL and the tier.
4. The user opens the URL. The page trades its one-time ticket for a viewer JWT and subscribes to its field of view.
5. Prayer loop: each accepted prayer is checked, written to SpacetimeDB and debited from the budget (see MCP requirements).
6. The priest departs when the budget is spent or a disconnect is detected. It walks to the nearest stand, lights a candle and walks out, and its row is removed after the animation.
7. A scheduled reducer puts the candle out when its burn time ends.

When the viewer's own priest has gone, the page fades to a closing card ("Ite, missa est") and drops its subscription.

## MCP requirements

The gate is a remote MCP server over streamable HTTP at `https://<gate>/mcp`. It uses OAuth 2.1 as the MCP authorization spec requires, with GitHub as the upstream identity provider. It exposes five tools and no resources. Every tool result is a fixed template filled with numbers, ids and the URL, and never contains anyone's prayer text, intention or name.

### Plugin

The plugin is a folder `indulgence/` with no executable code. Check the layout against the current Claude Code plugin docs.

- `.claude-plugin/plugin.json`: manifest (name, version, description).
- `.mcp.json`: `{"mcpServers":{"indulgence":{"type":"http","url":"https://<gate>/mcp"}}}`.
- `commands/indulgence.md`: the slash command.
- `agents/priest.md`: the priest subagent.

**`/indulgence [budget] [intention]` command.** It takes `$ARGUMENTS`. The budget is an optional leading number with an optional `k` or `m` suffix, and the rest is the intention. The command prompt tells the main model to:

1. Call `begin` with `intention` set to the user's words *verbatim*, and with `budget_tokens`.
2. Print the returned URL and nothing else.
3. If `mode` is `sampling`, call `vigil(session_id)` repeatedly until it returns `done: true` or `mode: "pray"`.
4. If `mode` is `pray`, launch the `priest` subagent with a prompt containing only the session id and the intention verbatim. It must not add to, summarise or rephrase anything. When the subagent returns with `done: false`, launch a fresh one; this caps each subagent's context.
5. When finished, reply "Your candle is lit." and nothing else.

Also `/indulgence forget`, which calls `forget`.

**`priest` subagent frontmatter:** `name: priest`, `tools: mcp__indulgence__pray` (the allowlist is the hard boundary, so no Read, Bash, Grep or web tools), `model: inherit`. The system prompt asks it to:

- Compose one prayer per call in the style of medieval Latin liturgy (collects, litanies, versicles and responses), for the soul named in the intention.
- Use only the intention: no code, files, projects, tools, people or places from anywhere else.
- Output Latin only, at most 120 words per prayer.
- Call `pray` with `tier: "subagent"`, at most 10 times, then return the last `done` value.

### Tiers

| Tier | When | Context the model sees | Mutuals see |
| --- | --- | --- | --- |
| Sampling | Client declared the `sampling` capability at initialize | Gate's system prompt plus intention only (`includeContext: "none"`) | Real prayer text |
| Subagent | Plugin installed, no sampling | Agent prompt, the delegation message, possibly CLAUDE.md | Real prayer text |
| In-session | Any other MCP client | The whole conversation | Canned prayers only |

The gate picks `sampling` or `pray` mode at `begin` from the client's capabilities. The subagent and in-session tiers are self-reported through `pray`'s `tier` argument. Lying about it only exposes the liar's own text to their own mutuals.

### Tools

| Tool | Arguments | Returns | Behaviour |
| --- | --- | --- | --- |
| `begin` | `intention` string, at most 140 chars; `budget_tokens` int, default 10,000, min 1,000, max 1,000,000 | `session_id`, `url`, `mode` (`sampling` or `pray`), `budget_tokens` | Creates the session and calls the module's `enter` reducer. If the account already has a live priest, that priest departs first (takeover). Rate limit: 10 per hour per account. |
| `vigil` | `session_id` | `done`, `mode`, `prayers`, `spent`, `left` | Sampling mode only. Runs for at most 5 minutes per call, sending one sampling request per pacing slot. After 3 consecutive refused or failed requests it returns `mode: "pray"` so the command falls back to the subagent. |
| `pray` | `session_id`; `text` at most 1,200 chars; `tier` (`subagent` or `in_session`) | `done`, `accepted`, `left` | Checks the text (Safety guardrails), debits the budget and calls `post_prayer`. It holds the response until the pacing slot ends. A rejected prayer is not debited, and the result is `accepted: false` with no reason text. |
| `depart` | `session_id` | `ok` | Explicit exit; disconnect detection calls the same path. |
| `forget` | none | `ok` | Ends any live session, then deletes the account, follow edges, sessions and candles. |

### Budget and pacing

The budget is counted in prayer tokens, not billed tokens. The gate cannot see real usage, so `spent` is estimated from accepted text as `ceil(chars / 3)`. Real cost is higher because of system prompts, context and per-call overhead; `begin`'s template says roughly 2 to 5 times.

There is one pacing slot every 20 seconds per session. `pray` and `vigil` never accept a second prayer within 20 seconds of the last. The default 10,000-token budget is about 50 prayers, or roughly 17 minutes.

When `spent >= budget`, the next call returns `done: true` and the gate departs the priest.

### Sampling request

- `systemPrompt`: the fixed priest persona, the same rules as the subagent.
- `messages`: one user message, `Intentio: <intention>`, with the intention cleaned up as described in Safety guardrails.
- `includeContext: "none"`, `maxTokens: 300`, `temperature: 1`, no `modelPreferences`, so the user's own model is used.
- Clients may ask the user to approve each request. Accept that, and don't try to get around it.

### Disconnects and Ctrl+C

Every MCP request on a session sets `last_seen`. The gate departs the priest on whichever of these happens first:

- A clean shutdown: the client sends `DELETE /mcp` for the session. Depart at once.
- A cancelled tool call (`notifications/cancelled`, such as Esc or Ctrl+C in Claude Code). Wait 90 seconds; if no `pray` or `vigil` call arrives, depart.
- Silence: `now - last_seen > 180 s`. The gate's own timer departs the priest.
- Gate crash backstop: the module's `reap_stale` reducer departs any priest whose `last_seen` is more than 5 minutes old.

## Geometry of the cathedral

The cathedral is an endless row of identical 30-tile bays along x. Each bay has its own altar, four rows of pews split by a centre aisle, and an arcade on each side that it shares with the neighbouring bay. A viewer only ever sees about one bay around their own priest.

&#91;embedded content: plan view of one bay · tile coordinates\]

Plan view in world tiles: x runs along the endless axis, and y runs from the altar (y = 0) to the back wall (y = 14). Priests enter and leave through the door in the back wall.

### Coordinates and constants

World positions are tiles. Bay index b is any integer, positive or negative, and a bay's tile x runs from 30b to 30b + 29. Arcade a sits at bay-local x 0–4, between bay a − 1 and bay a. All constants live in one shared file used by the module, the gate and the client.

| Constant | Value | Notes |
| --- | --- | --- |
| `BAY_W` | 30 tiles | Bay width, including one arcade |
| `ARCADE_X` | local x 0–4 | Arcade strip; columns plus one votive stand |
| `ALTAR` | local x 14–20, y 1–3 | Centred on the aisle |
| `ROW_Y` | 6, 8, 10, 12 | Row 0 is nearest the altar |
| `LEFT_SEATS` | local x 15 down to 8 | Seat index i = 0 at the aisle end |
| `RIGHT_SEATS` | local x 19 up to 26 | Seat index i = 0 at the aisle end |
| `AISLE_X` | local x 16–18 | Door at the back wall, y = 14 |
| `STAND` | local x 1–3, y 7–11 | 40 candle slots, 4 tiers of 10 |
| Seats per bay | 64 | 4 rows × 2 halves × 8 |

A seat's address is (b, row, half, i), and its world position is:

```latex
x = 30b + \begin{cases} 15 - i & \text{left half} \\ 19 + i & \text{right half} \end{cases}, \qquad y = 6 + 2\,\mathrm{row}
```

### Seating

Seating puts friends first, and spend only nudges a group forward. Seats are assigned inside the module's `enter` reducer, so assignment is transactional and never races. Priests are never moved after they sit down.

Notation: M(u) is the set of live priests who are mutuals of the newcomer u. d is the tile Manhattan distance. r(s) is the row of seat s. q(u) in \[0, 1\] is u's budget percentile among sessions started in the last 24 hours.

**If u has live mutuals,** the candidate set C is the free seats in every bay that holds a mutual, plus the bays either side of each. Choose

```latex
s^{*} = \arg\min_{s \in C} \; \sum_{v \in M(u)} d(s, p_v) \; + \; \mu \, (1 - q_u) \, r(s), \qquad \mu = 2
```

Break ties at random. With μ = 2, falling back a row costs at most 2 tiles of distance, so sitting near friends almost always wins and spend only breaks near-ties.

**If u has no live mutuals,** visit bays in the order 0, 1, −1, 2, −2, … and take the first bay with fewer than 48 live priests. Pick the row round(3(1 − q(u))), so higher spend sits further forward. Take a random free seat in that row, or else the nearest row with a free seat. The last 16 seats of each bay are kept free for arrivals with mutuals, so friends can still sit together later.

The cost is O(|M(u)| · |C|) per join, and C is at most 192 seats per mutual-holding bay. Departing priests stop counting towards occupancy straight away.

### Votive stands

A departing priest from the left half goes to arcade b and one from the right half goes to arcade b + 1. The candle takes the lowest free slot. If that stand is full, search the arcades outward by x distance.

### Spend tiers

Vestments come from the budget pledged at `begin`. Candle size and burn time come from prayer tokens actually spent at departure. All thresholds are tunable constants.

| Prayer tokens | Vestment | Candle | Burn time |
| --- | --- | --- | --- |
| Under 10,000 | Friar: brown habit | Taper | 24 h |
| 10,000–49,999 | Priest: black cassock, white stole | Votive | 30 h |
| 50,000–199,999 | Bishop: mitre and crozier | Pillar | 36 h |
| 200,000 and over | Cardinal: scarlet | Paschal candle | 48 h |

### Field of view and rendering

The camera centres on the viewer's own priest and shows a window 30 tiles wide along x, which is about one bay. The pew block (local x 8–26) then fills roughly two thirds of the screen. The client subscribes to x within ±40 tiles of its priest. That subscription never changes, because seated priests don't move.

- Projection: 2:1 isometric, tile 16 × 8 base pixels, screen position sx = (x − y) · 8, sy = (x + y) · 4.
- Pixel art: draw to a 480 × 270 offscreen canvas, scale up by an integer factor with `imageSmoothingEnabled = false`.
- Draw order: painter's sort by x + y, then by layer (floor, furniture, priests, flames).
- Hover: hit-test priest and candle sprites; show a card with the label the viewer is allowed to see (Stream requirements).

### Movement

All movement is animated on the client from `state` and `state_since`, at 4 tiles per second along fixed waypoints. The server stores only state changes.

1. `entering`: appear at the door, walk up the aisle to the row, step sideways to the seat and kneel.
2. `praying`: idle loop, with a speech bubble that types out the current prayer over the 20-second slot.
3. `departing`: walk to the aisle, then along the front gap (y = 5) to the stand, light the candle (2 s), and leave by the door. The server sets the candle's `lit_at` to departure + 8 s and deletes the priest row after 20 s.

## Stream requirements and spec

All live state reaches browsers through SpacetimeDB subscriptions; there is no custom WebSocket protocol. Public tables carry anonymous scene state. Each viewer's names and prayer text live in rows filtered to that viewer. Only the gate can call reducers.

### Tables

| Table | Visibility | Key columns | Purpose |
| --- | --- | --- | --- |
| `account` | Private | `identity`, `gh_hash`, `gh_login`, `gh_name`, `label_mode` (username or full name), `consent_at` | One row per GitHub user |
| `follow_edge` | Private | `owner_hash`, `other_hash` | Mutuals asserted by the owner's latest login |
| `session` | Private | `session_id`, `identity`, `tier`, `budget`, `spent`, `last_seen`, `cancel_at` | Live sessions; deleted 7 days after they end |
| `gate_service` | Private | `identity` | Identities allowed to call reducers |
| `priest` | Public | `priest_id`, `x`, `y`, `bay`, `row`, `half`, `seat`, `vestment`, `state`, `state_since` | Anonymous scene state |
| `prayer_tick` | Public | `priest_id`, `x`, `seq`, `canned_idx`, `at` | Latest prayer slot per priest; strangers see canned prayer `canned_idx` |
| `candle` | Public | `candle_id`, `x`, `y`, `arcade`, `slot`, `size`, `lit_at`, `expires_at`, `label` | `label` is the public candle name |
| `viewer_label` | Per viewer | `viewer`, `priest_id`, `label` | Hover names: rows exist only for the viewer's mutuals and themselves |
| `prayer_text` | Per viewer | `viewer`, `priest_id`, `seq`, `text`, `at` | Real prayer text for the owner and eligible mutuals; last 3 per pair |

Per-viewer tables use SpacetimeDB row-level security, a client visibility filter of the form `WHERE viewer = :sender`. Check its status in the version you use. If it isn't usable, the gate serves those two tables over a small authenticated WebSocket, and everything else stays the same.

### Reducers

Every reducer checks that `ctx.sender` is in `gate_service`. Viewers can subscribe but cannot write.

| Reducer | Called by | Effect |
| --- | --- | --- |
| `upsert_account` | Gate, after login | Writes the account row; replaces the owner's `follow_edge` rows |
| `enter` | Gate, from `begin` | Seats the priest (Geometry); inserts `priest` as `entering`; writes `viewer_label` rows both ways for live mutuals |
| `post_prayer` | Gate, from `pray` or `vigil` | `spent += tokens`; upserts `prayer_tick`; sets `state = praying` on the first prayer; writes `prayer_text` for the owner, and for live mutuals if the tier allows |
| `heartbeat` | Gate | Updates `last_seen` |
| `depart` | Gate | `state = departing`; inserts `candle`; deletes the session's `prayer_text` and `viewer_label` rows; schedules `remove_priest` in 20 s |
| `remove_priest` | Scheduled | Deletes the `priest` and `prayer_tick` rows |
| `expire_candles` | Scheduled, every 5 min | Deletes candles past `expires_at` |
| `reap_stale` | Scheduled, every 60 s | Departs sessions with `last_seen` more than 5 min old |
| `forget` | Gate | Deletes the account and all of its rows |

`viewer_label` is written only when both priests are live. A mutual who arrives later gets labels for everyone already present, and those people get a label for the newcomer.

### Subscriptions

The client gets its own priest's x (`px`) from the viewer JWT's `px` claim, then subscribes once:

```sql
SELECT * FROM priest      WHERE x >= {px - 40} AND x < {px + 40};
SELECT * FROM prayer_tick WHERE x >= {px - 40} AND x < {px + 40};
SELECT * FROM candle      WHERE x >= {px - 40} AND x < {px + 40};
SELECT * FROM viewer_label;
SELECT * FROM prayer_text;
```

The last two return only the viewer's own rows because of the visibility filter.

### Rates and sizes

- `priest` rows change about 3 times per session (enter, first prayer, depart).
- `prayer_tick` changes once per prayer, at most every 20 s per priest. A full window holds about 170 priests, so at most about 9 updates per second at under 100 bytes each, which is under 1 KB/s.
- `prayer_text` rows are at most 1,200 chars, and each viewer gets at most one per mutual every 20 s.
- Candles change on light and expiry only.

### Client behaviour

- Work out clock skew from the first server timestamp. Animate from `state_since` and `lit_at`.
- Bundle the canned prayers: Pater Noster, Ave Maria, Gloria Patri, Confiteor, Salve Regina, Anima Christi, Agnus Dei, Kyrie, Requiem aeternam. All are pre-1929 public-domain texts. Strangers see `canned_idx` mod the list length.
- Show a prayer as a typewriter speech bubble over its 20-second slot. Hovering shows the full text.
- Draw all text with canvas `fillText`. Never put any string from the database into the DOM as HTML.
- On losing the connection, retry with backoff for 2 minutes, then show the closing card.

### Viewer access

- `begin` returns `https://<site>/#t=<ticket>`. The ticket sits in the fragment so it never reaches server logs or `Referer` headers.
- Ticket: 128-bit random, single use, expires after 10 minutes, bound to one session.
- The page POSTs the ticket to `https://<gate>/viewer-token` and gets back a JWT. Claims: `iss` = gate; `sub` = the user's stable viewer subject (so the SpacetimeDB identity is the same every session); `aud` = the SpacetimeDB module; `role: viewer`; `px`; `exp` = 4 hours, refreshed by the page while the session is live.
- The JWT is kept in `sessionStorage` only. A second use of a ticket is refused, and a fresh `begin` issues a new one.

## Safety guardrails

The design depends on three rules: nothing user-written ever goes back into a model's context, prayers come from the narrowest context available, and only the gate can write. Each of the controls below must be covered by a test.

| Threat | Guardrail |
| --- | --- |
| Prompt injection through tool results | Tool results are fixed templates filled with numbers, ids and the URL. They never contain prayer text, intentions, names, or the reason a prayer was rejected. A test asserts this for every tool. |
| Session context leaking into prayers | Tiers (MCP requirements): sampling uses `includeContext: "none"`; the subagent's only tool is `pray`; in-session prayers are never shown to mutuals. `begin`'s result tells in-session users that only they will see their prayers. |
| Leak-shaped text | Reject a prayer that contains a URL, a path separator, `@`, braces or brackets, `=` or `;`, a file extension, a camelCase or snake\_case token, or 5 or more digits in a row. A rejected prayer is not debited. |
| Abusive or spam text reaching mutuals | Latin check: at least 60% of words must appear in a bundled Latin wordlist of about 20k forms. A multilingual slur denylist. Limit of 1,200 chars. NFC normalisation, then strip control, zero-width and bidi characters. Drawn with canvas only. Viewers can mute any priest client-side. |
| Intention text | At most 140 chars, same cleaning and denylist. Only ever shown to its owner. Wrapped as `Intentio: …` in sampling. Deleted when the session ends. |
| Public candle names | GitHub logins have a safe character set. Full names (opt-in) go through the denylist and a 40-char cap and are drawn with canvas only. |
| Sockpuppets and spam | GitHub account at least 7 days old. One live priest per account (takeover). `begin` limited to 10 per hour per account. 20-second pacing enforced on the server. Per-IP limits at the gate. Global cap of 5,000 live sessions. |
| Spend gaming | Spend is estimated from accepted text only and is cosmetic. Reject prayers that compress too well (gzip ratio under 0.25) as padding. Otherwise rely on the honour system, and say so. |
| Viewer token theft | Ticket in the URL fragment, single use, 10-minute expiry. The JWT is view-only, kept in `sessionStorage`, and expires after 4 hours. |
| Unauthorised database writes | Every reducer checks `gate_service`. Viewer JWTs carry `role: viewer`, and the gate's own identity uses a separate signing subject. |
| Gate compromise | The GitHub client secret and JWT signing key live in a secret manager. User GitHub tokens are never stored. The JWKS has a `kid` so keys can be rotated. Follow edges are stored as HMAC hashes. |
| Supply chain | The plugin is Markdown and JSON only. Gate dependencies are pinned with a lockfile and kept to the MCP SDK, an OAuth library, a JWT library and the SpacetimeDB SDK. |
| Surprise costs | The budget is required to be bounded (max 1,000,000 prayer tokens). `begin` states the expected real cost multiple. Pacing caps throughput. |
| Sampling consent | Respect any per-request approval prompt the client shows. Never ask the model to approve on the user's behalf. |

Tool descriptions stay short and factual. They must not tell the model to do anything beyond calling the tool correctly.

## Privacy statement and disclaimers

The service keeps the least data it needs to seat priests and burn candles. Prayer text disappears when your priest leaves. Your candle name is public while it burns.

### What is collected

| Data | Why | Who can see it | Kept for |
| --- | --- | --- | --- |
| GitHub login | Identity; candle label | Everyone, on your candle while it burns | Until you run `forget` |
| GitHub display name | Candle and hover label, only if you opt in | Everyone on your candle; mutuals on hover | Until you opt out or run `forget` |
| GitHub numeric ID, stored as a keyed hash | Linking sessions to your account | No one | Until `forget` |
| Mutual follows, stored as keyed hashes | Seating you near friends | No one; the server only | Replaced at each login; deleted by `forget` |
| Intention text | Prompt for your prayers | Only you | End of session |
| Prayer text | Display | You; your mutuals if made by the sampling or subagent tier | Until your priest has left |
| Session times, budget, spend | Pacing, vestments, candle size | Your candle's size and presence show that you visited in the last day or two | 7 days after the session ends |
| IP address | Rate limiting | No one | 24 hours, in gate logs |

**Never collected:** your code, files or repositories; anything in your conversation outside /indulgence; your email; your GitHub access token, which is thrown away once your mutuals are worked out.

**Who sees what.** Strangers see an anonymous priest saying canned prayers, plus the names on candles. Your mutuals see your name when they hover over your priest, and read your generated prayers (not in-session ones). You see everything about your own priest.

## GitHub connection

A GitHub OAuth App that requests no scopes provides identity, and public follow lists provide mutuals. The user's GitHub token is used once at sign-in and then thrown away.

### App setup

- Type: OAuth App. Callback `https://<gate>/oauth/github/callback`.
- Scopes: none. The public profile and public follow lists need no scope, and email is not requested.
- Secrets: `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` and `EDGE_HMAC_KEY`, all in the gate's secret manager.

### Sign-in flow

The gate is the OAuth 2.1 authorization server that the MCP authorization spec expects Claude Code to find. Internally it delegates sign-in to GitHub.

1. Claude Code reads the gate's protected-resource and authorization-server metadata, registers itself (dynamic client registration) and starts an authorization-code flow with PKCE.
2. The gate's `/authorize` redirects to GitHub's authorize URL with an empty scope and a signed `state`.
3. GitHub calls back. The gate swaps the code for a user token.
4. The gate fetches `GET /user`. It refuses accounts less than 7 days old (`created_at`).
5. The gate fetches `GET /user/following` and `GET /user/followers`, 100 per page, up to 5,000 of each. Mutuals are the intersection by numeric id.
6. The gate discards the user token, without storing or logging it.
7. On first sign-in, the gate shows the consent screen in the browser and records the name choice.
8. The gate calls `upsert_account`, which replaces the user's `follow_edge` rows with `(HMAC(gh_id), HMAC(other_id))` for each mutual.
9. The gate issues its own MCP access token (1-hour lifetime) and a refresh token (30-day lifetime) to Claude Code.

### Mutuals

Each user's rows record what *their* latest sign-in saw. Two users count as mutuals if either of them asserted it:

```latex
\mathrm{mutual}(u, v) \iff (h_u, h_v) \in E \;\lor\; (h_v, h_u) \in E
```

Edges can be up to 30 days stale, because they refresh only when the user signs in again after the refresh token expires. This is the cost of not keeping GitHub tokens, and it is acceptable for seating.

### Limits and edge cases

- Users with more than 5,000 follows or followers get mutuals from the first 5,000 of each. Note this in the README.
- Steps 4 and 5 make at most 101 API calls, well inside GitHub's 5,000 per hour per-user limit.
- If the login changes on GitHub, the account row updates on the next sign-in, keyed by numeric id.
- If a user revokes the OAuth app, nothing breaks on the gate's side, because it holds no GitHub token. The refresh token keeps working until it expires, and `forget` is the way to remove data.
- Only public follows are used. No organisation membership is read.
